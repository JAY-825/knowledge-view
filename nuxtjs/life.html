# Nuxt.js 生命周期

Nuxt.js 生命周期指的是一个 Nuxt 应用从启动、匹配路由、执行中间件、拉取数据、服务端渲染、客户端激活，到后续页面切换和组件卸载的整个运行过程。

如果只会写页面和组件，但不了解生命周期，就很容易在错误的阶段里做错误的事情，例如：

  • 在服务端执行只能在浏览器运行的代码
  • 在页面还没准备好时就访问 DOM
  • 在路由切换时重复请求数据
  • 在组件卸载后仍然保留定时器和监听器
  • 搞不清中间件、插件、页面数据请求到底谁先执行

理解生命周期之后，你会更容易判断：

  • 某段代码应该写在插件、中间件还是页面里
  • 某个请求应该在服务端执行还是客户端执行
  • 某个副作用应该在挂载时开始，还是在卸载时清理
  • 页面首次加载和前端路由跳转时行为为什么不同

本文以 Nuxt 3 为主，系统讲解 Nuxt.js 生命周期的主要阶段、常见钩子以及实际开发中的使用建议。

# 为什么要理解生命周期

Nuxt 并不是一个只有页面和组件的简单框架，它同时涉及：

  • Vue 组件生命周期
  • 服务端渲染生命周期
  • 客户端激活生命周期
  • 路由导航生命周期
  • 插件初始化生命周期
  • 页面数据获取生命周期

这些生命周期会互相叠加。如果不了解顺序，最常见的问题就是“代码能运行，但时机不对”。

例如下面这些情况都和生命周期密切相关：

  • 登录校验应该放在路由中间件，而不是组件挂载后才判断
  • 首屏数据希望被 SSR 输出，就应该在页面渲染前获取
  • 依赖 window、document 的逻辑应放到客户端阶段
  • 离开页面时需要清理监听器，避免内存泄漏

# Nuxt 生命周期的整体视角

先从全局理解一次 Nuxt 页面访问的大致流程。

# 首次访问页面时

用户第一次访问某个 Nuxt 页面，通常会经历这些步骤：

  1. Nuxt 应用初始化
  2. 执行插件
  3. 匹配目标路由
  4. 执行路由中间件
  5. 创建页面和布局
  6. 执行页面中的数据获取逻辑
  7. 服务端渲染 HTML
  8. 浏览器接收 HTML 并展示首屏
  9. 客户端接管页面并完成激活
  10. 页面进入可交互状态

# 在客户端切换页面时

如果已经进入应用，之后通过前端路由切换页面，流程会更偏向客户端：

  1. 点击链接或调用 navigateTo
  2. 匹配新路由
  3. 执行路由中间件
  4. 执行新页面的数据获取逻辑
  5. 更新页面组件树
  6. 挂载新组件，卸载旧组件
  7. 触发相关页面和组件钩子

也就是说，Nuxt 生命周期并不是单一的一套钩子，而是“应用生命周期 + 路由生命周期 + 页面生命周期 + Vue 组件生命周期”的组合。

# 生命周期的核心阶段

从开发角度看，可以把 Nuxt.js 生命周期拆成以下几个主要阶段：

  • 应用创建阶段
  • 插件初始化阶段
  • 路由解析与中间件阶段
  • 数据获取阶段
  • 服务端渲染阶段
  • 客户端激活阶段
  • 页面切换阶段
  • 组件卸载与资源清理阶段

下面分别展开。

# 一、应用创建阶段

当 Nuxt 应用启动时，会先完成应用级初始化。这个阶段决定了项目的基础运行环境。

# 这一阶段通常会发生什么

  • 读取 nuxt.config.ts
  • 初始化模块与运行时配置
  • 创建 Vue 应用实例
  • 注入插件、组合式函数和全局能力

在业务开发里，这一阶段最常接触的是：

  • nuxt.config.ts
  • plugins/
  • app.vue

# nuxt.config.ts 的角色

nuxt.config.ts 更像“应用配置入口”，它本身不是运行时生命周期钩子，但它会决定生命周期中的很多行为，例如：

  • 是否开启 SSR
  • 运行时环境变量
  • 自动导入规则
  • 插件注册
  • 路由规则
// nuxt.config.ts
export default defineNuxtConfig({
  ssr: true,
  runtimeConfig: {
    apiSecret: "",
    public: {
      apiBase: "/api",
    },
  },
});

# 二、插件初始化阶段

Nuxt 在应用创建过程中会执行 plugins/ 目录下的插件。插件非常适合做“应用启动时只初始化一次”的逻辑。

# 插件适合做什么

  • 注册全局方法
  • 注入第三方 SDK
  • 封装请求实例
  • 初始化埋点、日志、主题、权限工具

# 插件示例

// plugins/api.ts
export default defineNuxtPlugin(() => {
  const api = $fetch.create({
    baseURL: "https://example.com/api",
  });

  return {
    provide: {
      api,

});

# 客户端插件与服务端插件

Nuxt 支持按运行端拆分插件：

  • plugins/xxx.client.ts 只在客户端执行
  • plugins/xxx.server.ts 只在服务端执行
  • plugins/xxx.ts 两端都可能执行

例如浏览器存储、window 事件监听、更适合写在客户端插件中：

// plugins/theme.client.ts
export default defineNuxtPlugin(() => {
  const theme = localStorage.getItem("theme") || "light";
  document.documentElement.dataset.theme = theme;
});

# 插件的生命周期理解

可以把插件理解为：

  • 先于页面渲染执行
  • 用于给后续生命周期阶段提供基础能力
  • 通常在应用启动时初始化

因此，公共请求实例、鉴权工具、全局注入都很适合放在这里。

# 三、路由解析与中间件阶段

当用户访问某个页面时，Nuxt 会先匹配路由，然后执行中间件，再决定是否继续进入页面。

这个阶段的重点是“页面能不能进入”以及“进入前要不要做前置处理”。

# 中间件适合做什么

  • 登录校验
  • 权限判断
  • 页面跳转重定向
  • 根据角色切换布局
  • 根据参数做前置判断

# 中间件示例

// middleware/auth.ts
export default defineNuxtRouteMiddleware((to, from) => {
  const token = useCookie("token");

  if (!token.value) {
    return navigateTo("/login");
  }
});

# 中间件执行时机

一般来说，中间件发生在页面真正渲染之前。

这意味着：

  • 如果中间件重定向了，页面组件可能根本不会进入挂载阶段
  • 权限判断放在中间件里比放在 onMounted 里更合理
  • 首屏 SSR 时，中间件也可能在服务端参与执行

# 全局中间件

如果希望每次路由切换都执行，可以定义全局中间件。

// middleware/log.global.ts
export default defineNuxtRouteMiddleware((to, from) => {
  console.log("路由切换：", from.fullPath, "=>", to.fullPath);
});

# 四、数据获取阶段

页面进入前或渲染前，往往需要先拿到数据。Nuxt 3 中常见的数据获取方式有：

  • useAsyncData
  • useFetch
  • 普通 await
  • 组件挂载后的客户端请求

其中，真正与 Nuxt 生命周期强相关的是 useAsyncData 和 useFetch。

# useAsyncData

它常用于页面级异步数据获取，并能够和 SSR 配合。

<script setup>
const { data: article, pending, error } = await useAsyncData("article", () => {
  return $fetch("https://example.com/api/article/1");
});
</script>

<template>
  <div>
    <p v-if="pending">加载中...</p>
    <p v-else-if="error">加载失败</p>
    <div v-else>{{ article }}</div>
  </div>
</template>

# 这一阶段的关键理解

如果在页面顶层 await useAsyncData() 或 await useFetch()：

  • 首次访问时，服务端通常会先拿到数据再输出 HTML
  • 客户端激活时会复用已注入的数据，避免重复请求
  • 页面切换时会根据导航重新执行数据拉取

这正是 Nuxt 首屏体验好的原因之一。

# 普通 onMounted 请求和 SSR 请求的区别

下面这种写法也能请求数据：

<script setup>
const list = ref([]);

onMounted(async () => {
  list.value = await $fetch("/api/posts");
});
</script>

但它通常发生在客户端挂载后，因此：

  • 首屏 HTML 中往往没有数据内容
  • 用户可能先看到空白或骨架屏
  • 更适合必须依赖浏览器环境的请求

因此，页面首屏核心数据通常更推荐放在 useAsyncData 或 useFetch 中。

# 五、服务端渲染阶段

如果项目开启 SSR，Nuxt 在首次请求时会在服务端完成页面渲染。

# 服务端渲染阶段会做什么

  • 创建当前请求对应的应用上下文
  • 执行可在服务端运行的插件和中间件
  • 拉取页面所需数据
  • 渲染页面 HTML
  • 将数据状态一并注入到页面中

# 服务端阶段的特点

  • 没有浏览器 DOM
  • 没有 window、document、localStorage
  • 更适合首屏数据预取、SEO 输出、权限前置判断

# 服务端阶段常见错误

下面这种代码如果在服务端执行就会出问题：

const token = localStorage.getItem("token");
1

因为服务端没有 localStorage。

更稳妥的做法是：

  • 使用 useCookie()
  • 将逻辑放到 .client.ts 文件
  • 或通过 import.meta.client 判断运行端

例如：

if (import.meta.client) {
  const token = localStorage.getItem("token");
}
1
2
3

# 首次请求的大致顺序

在 SSR 场景下，一次页面访问可以粗略理解为：

  1. 浏览器请求某个 URL
  2. Nuxt 服务端收到请求
  3. 匹配页面路由
  4. 执行中间件
  5. 执行页面数据获取
  6. 渲染布局与页面
  7. 返回 HTML 和初始状态

这是 Nuxt 生命周期里最重要的一段，因为它直接影响：

  • 首屏速度
  • SEO
  • 数据是否提前可见

# 六、客户端激活阶段

浏览器拿到服务端输出的 HTML 后，并不意味着生命周期结束。接下来 Nuxt 还需要在客户端把页面“激活”。

这个过程叫 Hydration，也就是激活。

# 客户端激活是什么意思

服务端只负责生成 HTML 结构，而交互能力要在浏览器里由 Vue 接管。

激活阶段会做这些事：

  • 加载客户端 JavaScript
  • 创建浏览器端应用实例
  • 将现有 HTML 与组件树对应起来
  • 恢复事件监听、响应式、交互能力

# 激活阶段的典型问题

如果服务端输出的结构和客户端初次渲染结果不一致，就可能出现“激活不匹配”。

例如：

  • 服务端和客户端使用了不同随机数
  • 直接使用当前时间并立即渲染
  • 客户端依赖浏览器宽度决定结构

比如：

<template>
  <div>{{ Math.random() }}</div>
</template>
1
2
3

服务端和客户端的随机值不同，就可能导致激活警告。

# 规避思路

  • 避免在模板中直接使用不稳定数据
  • 把仅客户端可确定的内容放到 onMounted
  • 使用 ClientOnly 包裹只应在浏览器渲染的组件
<template>
  <ClientOnly>
    <ChartPanel />
  </ClientOnly>
</template>

# 七、页面挂载与 Vue 组件生命周期

Nuxt 页面本质上仍然是 Vue 组件，因此会经历 Vue 自己的生命周期。

最常用的钩子包括：

  • onBeforeMount
  • onMounted
  • onBeforeUpdate
  • onUpdated
  • onBeforeUnmount
  • onUnmounted

# onMounted

它会在组件挂载到浏览器 DOM 后执行，最适合处理：

  • DOM 操作
  • 第三方图表实例初始化
  • 浏览器事件绑定
  • 只应在客户端运行的代码
<script setup>
onMounted(() => {
  console.log("页面已经挂载到浏览器");
});
</script>

# 在 Nuxt 中如何理解 Vue 生命周期

可以简单记住：

  • Nuxt 负责应用、路由、数据和 SSR 生命周期
  • Vue 负责组件实例自身的生命周期

两者不是冲突关系，而是嵌套关系。

# 八、页面切换阶段

当用户在已经打开的 Nuxt 应用中继续访问其他页面时，会进入客户端路由导航阶段。

# 页面切换时通常会发生什么

  1. 用户触发导航
  2. Nuxt 匹配新路由
  3. 执行中间件
  4. 拉取新页面数据
  5. 更新布局或页面组件
  6. 卸载旧页面组件
  7. 挂载新页面组件

# 首次加载和页面切换的区别

首次加载更强调：

  • 服务端渲染
  • 首屏 HTML 输出
  • 客户端激活

页面切换更强调：

  • 客户端导航
  • 页面数据重取
  • 组件卸载与重建

因此，你会发现同一段代码在首次访问和二次跳转时的表现并不完全一样。

# 九、生命周期中的常见运行端判断

在 Nuxt 中，很多逻辑需要区分“服务端执行”还是“客户端执行”。

# 常见判断方式

if (import.meta.client) {
  console.log("当前运行在客户端");
}

if (import.meta.server) {
  console.log("当前运行在服务端");
}

# 十、Nuxt 应用级 Hook

除了 Vue 的组件生命周期和路由中间件外，Nuxt 还提供了一些应用级 Hook，用于监听应用运行过程中的关键事件。

这类能力通常通过 nuxtApp.hook() 使用。

# 示例：监听页面切换事件

// plugins/page-hooks.client.ts
export default defineNuxtPlugin((nuxtApp) => {
  nuxtApp.hook("page:start", () => {
    console.log("页面开始切换");
  });

  nuxtApp.hook("page:finish", () => {
    console.log("页面切换完成");
  });
});

# 这类 Hook 有什么用

  • 控制全局 loading 状态
  • 记录埋点日志
  • 做页面切换性能统计
  • 统一处理某些导航副作用

对于大型项目，这类应用级 Hook 很有价值，因为它观察的是“应用行为”而不是某个单独组件。

# 十一、页面生命周期中常见文件的职责

为了更清楚地理解生命周期，可以把常用目录和文件对应到具体阶段。

文件或目录 主要职责 更靠近哪个阶段
nuxt.config.ts 应用配置 应用初始化阶段
plugins/ 注入全局能力 插件初始化阶段
middleware/ 导航前置逻辑 路由解析阶段
layouts/ 页面外层结构 页面渲染阶段
pages/ 页面内容与页面级数据逻辑 路由与页面生命周期
components/ 可复用 UI 模块 Vue 组件生命周期
composables/ 逻辑复用 贯穿多个生命周期阶段
server/api/ 服务端接口 服务端请求处理

这样划分之后，你在写代码时会更容易判断“逻辑应该放在哪里”。

# 十二、实际开发中的典型场景

下面用几个常见问题帮助你把生命周期和实际开发对应起来。

# 场景 1：登录校验应该写在哪里

推荐写在 middleware/ 中，而不是 onMounted。

原因：

  • 中间件发生在页面进入之前
  • 能避免未登录用户先看到页面再被跳走
  • 更适合 SSR 场景下的权限前置控制

# 场景 2：首屏文章详情数据在哪里请求

推荐优先使用 useAsyncData 或 useFetch。

原因：

  • 可以参与 SSR
  • 首屏 HTML 直接包含内容
  • 更利于 SEO 和首屏体验

# 场景 3：图表库初始化应该写在哪里

推荐写在 onMounted 或客户端专属组件中。

原因：

  • 图表库一般依赖真实 DOM
  • 很多图表库依赖 window
  • 服务端没有这些浏览器能力

# 场景 4：离开页面时停止轮询

推荐写在 onUnmounted 中清理。

原因：

  • 页面切换时旧组件会被销毁
  • 若不清理，轮询会一直存在

# 场景 5：全局请求实例放在哪里

推荐放在 plugins/ 中。

原因：

  • 应用启动时统一初始化
  • 页面和组件都能复用
  • 生命周期位置清晰，不会到处重复创建

# 十三、一个完整的页面生命周期示例

下面用一个文章详情页串联一次比较完整的生命周期。

<!-- pages/article/[id].vue -->
<script setup>
definePageMeta({
  middleware: "auth",
  layout: "default",
});

const route = useRoute();

const { data: article, error } = await useAsyncData(
  () => `article-${route.params.id}`,
  () => $fetch(`/api/article/${route.params.id}`)
);

onMounted(() => {
  console.log("页面已挂载，可以安全操作 DOM");
});

onUnmounted(() => {
  console.log("页面卸载，执行清理逻辑");
});
</script>

<template>
  <div>
    <p v-if="error">文章加载失败</p>
    <article v-else>
      {{ article }}
    </article>
  </div>
</template>

# 十四、常见注意事项

# 1. 不要把浏览器专属代码直接写到通用上下文

例如：

  • window
  • document
  • localStorage
  • navigator

这些对象只在客户端存在。

# 2. 首屏核心数据不要都放到 onMounted

否则会导致：

  • SSR 失去优势
  • HTML 首屏内容不足
  • SEO 变差

# 3. 中间件是导航前处理，不是组件钩子

如果中间件直接重定向，页面组件可能不会进入挂载阶段。所以不要把页面级逻辑和中间件混为一谈。

# 4. 组件副作用必须清理

典型需要清理的内容包括：

  • 定时器
  • 事件监听
  • WebSocket 连接
  • 第三方实例

# 5. 首次渲染和客户端跳转不是完全同一条链路

首次渲染可能经历 SSR 和激活，而客户端跳转通常不重新走整页 HTML 输出流程。排查问题时一定要区分这两种情况。

# 十五、学习 Nuxt 生命周期的建议顺序

如果你是初学者，建议按下面顺序理解：

  1. 先理解 Vue 组件生命周期
  2. 再理解 Nuxt 的页面、布局、路由关系
  3. 然后掌握中间件执行时机
  4. 再学习 useAsyncData、useFetch 和 SSR
  5. 最后再接触插件和应用级 Hook

这样更容易建立完整认知，不会在一开始就被大量概念打乱。

# 总结

Nuxt.js 生命周期的核心点如下：

  • 应用启动时会先完成配置读取和插件初始化
  • 路由进入页面前会先执行中间件
  • 页面首屏数据通常在渲染前获取，以便参与 SSR
  • 服务端负责输出 HTML，客户端负责激活页面交互
  • 页面和组件仍然遵循 Vue 自身的生命周期
  • 页面切换时会重新经历路由、中间件、数据获取和组件更新
  • 浏览器相关逻辑应放在客户端阶段
  • 副作用逻辑要在卸载阶段及时清理

真正掌握 Nuxt.js 生命周期后，你会更清楚每段代码应该放在哪个阶段执行，也更容易写出结构清晰、性能合理、行为稳定的 Nuxt 应用。
